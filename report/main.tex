\shorttitle{Composer Classification with Deep Learning}

\abstract{This paper compares two deep learning models that classify classical
  MIDI files as works by Bach, Beethoven, Chopin, or Mozart. We removed unreadable
  files and exact duplicates. We then placed each file into a fixed training,
  validation, or test split. Movements from the same work were not kept together.
  The long short-term memory (LSTM) and convolutional neural network (CNN) models
  use sequences of pitch, velocity, note duration, and time between notes. Class
  weights reduce the effect of an uneven class distribution. We addressed
  overfitting with weight decay and validation-based early stopping. In one
  seeded MPS run, the CNN reached .822 validation accuracy and .812 weighted F1.
  The LSTM reached .759 accuracy and .748 weighted F1. The CNN may have benefited
  from learning short local note patterns, but one run cannot prove why it
  performed better. Even after addressing overfitting, the CNN reached .982
  training accuracy compared with .822 validation accuracy. This gap shows that
  substantial overfitting remained. The controls were likely not strong enough:
  the 106,916-parameter CNN had only 1,125 training files, dropout was applied
  only after pooling, no data augmentation was used, and training reached the
  20-epoch limit before early stopping could trigger. The CNN was the stronger
  model on this validation split, but the results do not yet show reliable
  performance on new musical works. Future work should group files by musical
  work, repeat the experiment, and evaluate the final models once on the
  untouched test set.}

\keywords{composer classification, MIDI, deep learning, LSTM, CNN, music information retrieval}

Automatic composer identification asks a simple question: who wrote a piece of
music? MIDI files store notes, timing, and duration directly. Unlike audio, they
do not include differences caused by singers, instruments, microphones, or
recording rooms. This makes MIDI useful for models that learn musical sequences
and patterns.

\section{Related Work}
\textcite{Hochreiter1997} introduced the long short-term memory architecture,
which can learn relationships across a sequence. This makes it suitable for
ordered musical notes. \textcite{LeCun2015} describe convolutional networks,
which learn short local patterns. \textcite{Kingma2015} introduced Adam, the
optimizer used to train both models.

Earlier studies often combine selected musical features with statistical or
machine-learning models. \textcite{Conklin2013} showed that several views of a
musical piece can improve classification. \textcite{McKay2018} presented
jSymbolic, a tool for extracting features from symbolic music. Our models learn
from note sequences instead. We use summary features only for exploratory data
analysis (EDA).

\section{Method}

\subsection{Dataset}
This project uses the \textit{MIDI Classic Music} dataset from Kaggle
\parencite{FedorakND}. Kaggle lists it as Version 1 with an unknown license. The
dataset contains MIDI files from many composers. We kept files by Bach,
Beethoven, Chopin, and Mozart. The helper script
\texttt{src/prepare\_dataset.py} downloads the archive (when
\texttt{{\raise.17ex\hbox{$\scriptstyle\sim$}}/.kaggle/kaggle.json} is
configured) and extracts these four composer folders. It also creates filtered
copies for inspection, but the models do not use those copies.

The modeling pipeline scans the raw composer folders. It removes unreadable files
and exact duplicates. It then uses a fixed random seed to create a stratified
70/15/15 split for training, validation, and testing. The saved split is reused
unless the user asks to rebuild it. This keeps file assignments the same between
runs. However, the split does not group files by musical work, catalog number,
or collection. For example, movements of Mozart's Symphony No. 40, K. 550 appear
in all three splits. The validation score may therefore be too high for truly
new works. The master notebook reports the class counts.

After cleaning, 1,608 MIDI files remain. The training split has 1,125 files, the
validation split has 241, and the test split has 242. We removed 22 malformed or
duplicate files. Bach makes up about 63\% of the training data (709 files), while
Chopin makes up 8\% (92 files). Both models use class-weighted cross-entropy loss
to reduce bias toward Bach. We report validation accuracy, precision, recall, F1
scores, and confusion matrices. We do not use the test split during model
development.

\subsection{Computational Workflow}
Pixi provides a locked Python 3.12 environment, and the saved manifest keeps file
assignments fixed. After \texttt{pixi install}, users run \texttt{pixi run
prepare-dataset} to get the data and \texttt{pixi run notebook} to open the
master notebook. The code uses Apple MPS when available, then CUDA, and finally
the CPU. The environment and preprocessing steps can be repeated. Exact model
scores may still change because PyTorch is not forced to use deterministic
algorithms, and batch size differs by device. The notebook runs the workflow and
presents the results. Reusable code is stored in \texttt{src/}.

The first run saves EDA data to
\texttt{dataset/processed/eda\_metadata.csv}. Later runs load this file instead
of reading every MIDI file again. Users must refresh the file after changing the
data or split because the code does not check it automatically.

Three patterns helped guide feature selection. First, note density differs by
composer. Bach averages 9.3 notes per second, while Beethoven averages 14.5.
Raw note count is also tied to file length. Second, Bach has a smaller mean pitch
range ($M = 43.1$ semitones) than Beethoven and Chopin ($M \approx 62$). These
differences may come from instrumentation, arrangements, data sources, or MIDI
encoding, not only from composing style. Third, tempo and velocity may reflect
how a MIDI file was created rather than how the music was performed. We therefore
treat these values with care.

Principal component analysis (PCA) showed strong overlap between composers in
the first two components. This led us to test models that keep note order and
timing. However, the PCA plot leaves out 34.4\% of the standardized variance, and
we did not test a classifier based only on summary features. The plot therefore
does not prove that summary features cannot work.

The first PCA component explains 47.1\% of the variance, and the second explains
18.5\%. Together they explain 65.6\%, but the composers still overlap in the
plot. Note count and duration are also related ($r = .69$). For this reason, we
use note density and sequence features instead of relying only on total note
counts. Figure~\ref{fig:eda-analysis} shows both analyses, which use training

\subsection{Preprocessing and Feature Extraction}
For both models, notes are sorted by start time, pitch, and end time. Each note
has four values: pitch, velocity, duration, and time since the previous note.
Pitch uses values from 1 to 128, while zero marks padding. Every sequence is cut
or padded to 4,096 notes. We calculate the mean and standard deviation for the
continuous features from nonpadding training notes only. We then use those same
values for validation and test data. This prevents information from those splits
from entering the feature preparation step.

\subsection{Model Architectures}

\subsubsection{LSTM Model}
The LSTM changes each pitch into a 32-value embedding and joins it with the three
continuous features. A one-layer LSTM with 64 hidden units processes the
sequence. The model uses the state at the last real note, so padded notes do not
choose the prediction. It then applies 30\% dropout and a four-class output
layer.

\subsubsection{CNN Model}
The CNN uses the same pitch embedding and continuous features. It has three
convolution blocks with 64, 128, and 128 filters. The first two blocks use
five-note kernels and four-note max pooling. The third uses a three-note kernel.
Each convolution is followed by batch normalization and ReLU. Global max pooling
creates one representation for the file. The model then applies 30\% dropout and
a four-class output layer. Both models use the same files, normalization, class
weights, and validation-based selection process.

\subsection{Training}
Both baselines are trained for up to 20 epochs with Adam \parencite{Kingma2015}
at a learning rate of .001 and weight decay of $1\times10^{-4}$. Class weights
are $w_c = N/(K n_c)$, where $N$ is the number of training files, $K$ is the
number of classes, and $n_c$ is the number of files in class $c$. Gradients are
clipped at 1.0.

After each epoch, the model is tested on the validation split. We save the model
with the highest validation accuracy, using lower validation loss to break a tie.
Training stops after five epochs without a new best model. In this run, CNN
training accuracy reached 96.8\% at epoch 20, while validation loss varied. The
LSTM validation loss began to rise after epoch 10 even as training loss fell.
These patterns show that overfitting remained. We did not run a separate test to
measure the effects of weight decay or early stopping. We also did not use data
augmentation or evaluate the test split.

\section{Discussion}
The CNN performed better on the validation split, but this does not prove that it
will perform better on new works. The LSTM learns the order of the full sequence.
The CNN learns short ordered patterns and then uses global max pooling, which
removes their exact positions. Both models use note duration, velocity, and
timing that are missing from the EDA summaries.

We used class weights because Bach dominates the training data. However, we did
not train an unweighted model, so we cannot measure how much the weights helped.
In the same way, we cannot measure the separate effects of weight decay and early
stopping. These methods may have limited overfitting, but they did not remove it.
The CNN still has about a 16-point gap between training and validation accuracy.

Several factors may explain why overfitting remained. The CNN has 106,916
parameters but only 1,125 training files. Its 30\% dropout is applied only after
global pooling, so the convolution blocks receive no dropout. The training data
were not augmented. Early stopping also did not stop the CNN: its best model was
at epoch 18, and the run reached the 20-epoch limit before the five-epoch patience
period ended. These points are possible explanations, not proven causes, because
we did not run controlled comparisons. Choosing the best epoch from validation
results can also make the reported validation score look slightly better than it
would on new data. A final test score is therefore still needed.

The CNN may have done better because its filters can find short note patterns.
However, the CNN and LSTM also differ in size, normalization, pooling, and how
they handle padding. More runs and focused experiments are needed to find the
real cause.

The comparison is fair within this experiment because both models use the same
files, features, class weights, and selection process. Still, related movements
can appear in different splits. A final test on the current split would measure
performance on held-out files, not necessarily on completely new musical works.
The results also come from one seeded run. Repeating the experiment would show
how much the scores change from run to run.

\section{Conclusion}
This project builds a fixed file-level MIDI pipeline and compares LSTM and CNN
models. Pixi locks the software environment, the saved manifest keeps file
assignments fixed, and the notebook runs reusable code from \texttt{src/}. The
CNN scored higher in this validation run, but it also showed strong overfitting.
It is therefore the better model for this split, not a proven better choice for
all composer-classification tasks. Weight decay and early stopping addressed the
problem, but they were not enough to remove it. The likely reasons include the
CNN's size compared with the training set, dropout only after pooling, no data
augmentation, and a training limit that ended before early stopping could stop
the CNN. Controlled comparisons are needed to confirm the effect of each factor.

The most important improvement is to group files from the same work or collection
before splitting the data. This would keep related movements in one split. The
experiment should then be repeated with several seeds, deterministic PyTorch
settings, and the same batch size on every device. Results should include the
average score and the amount of variation between runs.

Future experiments should test one design choice at a time. These tests should
cover class weights, weight decay, early stopping, model size, and CNN pooling.
The CNN should also mask padded notes before global pooling so that file length
does not affect its representation. If overfitting remains, a smaller CNN,
stronger dropout, and careful pitch, tempo, or timing changes could be tested.
All choices should use validation data only. Once the design is fixed, the final
models should be evaluated once on an untouched test set grouped by musical work.
